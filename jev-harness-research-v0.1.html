    💡

    摘要（先给结论）：Jev 不是又一个聊天大模型，而是一个"不生成文本、单次并行吐出带概率分布的结构化判定"的小模型；它最适合替换 agent/harness 主循环里那些"窄、高频、封闭集、带 schema"的判定节点，而不适合开放式推理、长文本生成与精确计算。

    对 HarnessWindTunnel 的落地判断：值得做一轮 1–2 天的最小实测，但暂不建议直接上线生产路径。三个 P0 机会（法律屏引用断言五分类、Playground 判分兜底、风洞/演化屏失败标签批量归因）在形态上与 Jev 高度匹配；两个硬约束决定必须先实测——其一，Jev 官方只背书英文，中文短客服实测准确率仅约 64%、明显落后国产中文模型，而本项目是中文法律卷宗场景；其二，官方自认注入式文字可以移动答案，而本项目安全域（trap·gate·leak-check）对漏报接近零容忍。所有官方性能倍数均为厂商自跑口径、尚无独立复现，接入前应以自有数据做小流量 A/B。

    Jev 本体：能力、API、定价与限制

    它是什么：一个"判定模型"而非生成模型

    Jev 是 TypeSafe AI 的旗舰模型，也是官方定义的第一个 System One model——命名借用 Kahneman《Thinking, Fast and Slow》的"快思考"；模型名 Jev 致敬经济学家 William Stanley Jevons（Jevons 悖论）。官方宣称

    它与 LLM 根本不同：接收一份 state（文本 / JSON 对象 / 文本数组）+ 一组带类型的问题，在单次请求内并行返回带概率分布与置信度的结构化判定，不生成自由文本、无需再解析。训练方法命名为 RLCD（Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习），与 RLHF/RLVR 并列；采样方式为并行采样而非自回归逐 token。输入仅限文本，官方标注图像/音频/视频"not supported (yet)"。官方宣称

    三种 Question 原语（Choice / Score / Noul）

    请求顶层字段为 state、model、questions（map，key 为自定义问题 ID；问题 ID 不参与推理，仅用于按同名键取回结果）。三种类型可在单次请求内自由混用、并行独立评估，增加问题几乎不增加时延、不互相污染。官方宣称

    类型语义请求要点响应要点
    Choice从固定选项中选一个criteria 为"选项名→描述"的 map；最多 255 个选项，建议加 other/none of the abovechoice + probabilities（各选项概率，和为 1）+ confidence
    Score在有序等级上打分criteria 为有序数组，2–10 级，须用具体情境描述而非"中等/一般"score（等级概率加权均值，可落两级之间）+ probabilities + confidence
    Noul是否成立？返回为真概率instructions + 可选 criteria（描述 true/false 各指什么）仅 noul（0–1）；无单独 confidence（二值分布由单值完全描述）

    关键语义提醒：noul=0.5 表示 yes/no 等概率，不代表"中等程度"，要度量程度应改用 Score。官方建议把复杂判断拆成多个原子问题、在代码里加权组合（Composite scoring）。官方另称把 13 个问题合到一次调用，比 13 次单独调用便宜 11.5 倍、快 9.6 倍，答案不变——此为官方口径。官方宣称

    概率、calibration 与"拒答"机制

    • 概率分布：Choice/Score 的 probabilities 和为 1，Noul 为单值；所有答案被约束在你提供的选项/等级之内，官方称"数学上不可能越界"。官方宣称
    • Calibration：官方称经 RLCD 训练，概率针对结果做过校准（置信度越高、准确率越高）；但明确免责：calibration 是在一批预测上的统计性质，不保证单条答案正确，confidence=1.0 只表示分布集中。官方宣称
    • confidence 路由：confidence（仅 Choice/Score 返回）是从分布形状算出的 0–1 统计量。官方三段式用法：高置信自动执行 / 中置信请用户确认或加标记 / 低置信转人工。阈值按风险设定。官方宣称
    • 没有独立的 abstain API：官方的"我不确定"机制就是 confidence 阈值路由；另一种做法是给 Choice 加 other/none of the above 选项，让模型把概率压到该选项上。"abstain"在官方术语里是架构模式，不是字段。官方宣称

    官方自认的限制（jaggedness，9 类失效模式）

    官方专页《Jev 1.13 jaggedness》（最后复审 2026-09-17）列出 9 类已知失效模式，这是本项目最该逐条对照的"红线清单"。官方宣称

    1. 字面理解：按字面读，不揣摩言下之意；negation/scoping 被字面读。
    2. 数学与数字：不是计算器，不可靠计数，hex/RGB 等数字表示处理差；不要用 score 插值反推精确数值。
    3. 日期时间比较：把日期当文本读，不做有序量比较；日期抽取交给模型、比较放代码。
    4. 间接/多层推理：双重否定、多层间接指代掉点；System 2 式推理不适合。
    5. 塞满无关细节的大 state：无关内容当干扰项降低精度（context rot）；应先检索过滤再送 state。
    6. 对抗内容：state 默认不被当作敌意数据，注入式诱导可移动答案。
    7. instructions 与 criteria 矛盾（如 true 映射到"否"）会变差。
    8. 不保证结构性恒等式：官方反例——正/反两个 Noul 概率和为 0.72+0.47=1.19（不满足 P(not A)=1-P(A)）。
    9. 不做生成：强行链式 choice 又慢又差；要生成/抽取自由文本时配合正则或生成式模型。

    总结禁忌：把代码能精确算的事丢给模型；一个问题塞多个判断；System 2 多跳推理；state 超过问题所需。

    Jev 专门材料综述：接入点、社区反馈与正反两面

    LangChain《Building a Harness with Jev》：当前最清晰的参考架构

    LangChain 官方博客（2026-09-17）是本次调研最关键的一篇，直接回答"Jev 在 agent loop 里放哪"。官方宣称核心论点意译："Agent 在循环里跑——LLM 决定做什么、工具执行、模型评估结果、再继续……tool calling 和 structured output 让 agent 能集成，但每个决策仍要一次模型调用，agent loop 依然慢且贵。"LangChain 的判断是：Jev 不是 LLM 替代品，而是把 loop 里那些"窄、高频、结构化"的判定节点，从一次 LLM 调用换成 70–500ms 的并行判定。

    它把 Jev 封装为 TypeSafeClassifier（分类器，非 chat 模型），给出两个决策点：

    1. Model routing（模型路由中间件）：简单 lookup 不需要强力模型，让 Jev 先看用户消息，按 criteria 选 fast / powerful 模型；路由结果的 probabilities/confidence 留在 agent state 里可审计。
    2. Auto Mode（危险工具调用拦截）：在工具真正执行之前用 Jev 判定是否 risky，block 掉高风险调用（如 bash）。LangChain 点出：Claude Code / Codex / Cursor 这类 coding harness 都内置"危险动作先分类再执行"的 guardrail，但这一步长期锁在闭源 harness 里，现在可以开放给所有 agent。

    架构一句话：LLM 负责开放式推理与生成，Jev 负责 loop 里的快速结构化判定——Jev 是 decision layer，不是 replacement。

    唯一公开的大规模独立实测（正面与负面并存）

    开发者"艾特玖"在 dev.to 发布的 benchmark（2026-09-21）是目前最有价值的反面+正面数据：10 个公开数据集、约 22,500 次 API 调用、52.2M 输入 token、总成本 $2.19。第三方实测

    表现结果
    能用间接 prompt-injection 检测（InjecAgent 1105 条）：阈值 0.10 时 P/R 100%、0 误报，41.1% 流量可在 100% 准确率下自动处理；BEIR SciFact reranking：MRR 0.622→0.843、Hit@1 50%→78.3%；意图分类 SNIPS 7 类 97.9%、Banking77 77 类 80.3%；MetaTool 199 工具路由 96.5%；Shell 命令风险闸：100% 危险命令被拦、98.2% 安全命令放行
    不行模型难度路由：51%（无信号），预测不了另一个模型的 failure mode；轨迹失败归因：AUROC 0.560（随机水平），需要跨步因果推理；非英文：韩语 R@1 48.9% vs 英语 61.5%

    工程教训：正交分解+代码组合优于单问题提示（shell-gate 误报 14.5%→1.8%）；多标签决策先 choice 竞争再 noul 验证（multi-skill routing R@1 9.0%→81.0%）；"Low score is not a safety guarantee"——0–0.1 分桶里仍有 16.6% 恶意样本。结论定性：模型给出校准的局部判断，控制流由代码掌握。

    社区反馈的正反两面

    正面（已观察到的好体验）第三方实测社区个例：价格/时延感知好（独立实测单次 P50 约 0.30s、约 $0.00004）；结构化输出零解析，JSON 直接进 if 分支；典型分类任务强；confidence 做 gate 可行；生态上车快；官方罕见透明（jaggedness 页自列失败模式、自承认"价格可能补贴"）。HN 主帖约 1924 分，创始人 CompleteSkeptic 亲自下场答疑。

    负面 / 质疑社区个例第三方实测：

    • "can't hallucinate" 被普遍打回：HN 高赞共识——"type safety is not factual correctness"，错的值仍然是错的，只是错得"格式正确"；创始人本人在评论区同意"可能选错"。
    • 苹果对橘子的性能比较：Jev 不出文本、不做 CoT，拿它和做长 chain-of-thought 的 LLM 比延迟先天占优；官方自己也承认"短期输入对我方有利"。
    • Benchmark 禁令争议：HN 另一帖指出 TypeSafe ToU 1(v) 与 MCA 2.3(f) 禁止用户公开发布 benchmark/性能数据，与"欢迎质疑"姿态矛盾，被称"Oracle-style legal"。
    • 技术壁垒质疑：有开发者称 prefill 普通 LLM 前缀+约束生成 1 个 token 已能在 Qwen2.5-1.5B 上拿 2–3× speedup；HN 上有人用本机 0.1813s 跑通等价管线。
    • Prior art 纠纷：r/LocalLLaMA 用户自称 2025-03 就做了同架构（自引 arXiv:2503.23303、2510.01237），TypeSafe 未公开回应；架构相似性是发帖人单方面主张。
    • Adversarial / 注入：state 被当作 data，注入文字会改答案。黑盒：未公布权重、参数量、架构、训练数据。

    agent loop 内小决策TinyAgent（EMNLP 2024）/ Aviary（2412.21154）/ AgentFlux（2510.00229）；停止/循环判定为文献空白端侧小模型 function calling 追平 GPT-4；非前沿 agent 成本低至 100×；停步判定多为启发式Jev 最有机会卡位的空白决策点
    RAG 判定LLMLingua（2310.05736）/ RAGBench（2407.11005）微调的 RoBERTa 小模型在 RAG 评估上打败 LLM-as-judgeJev 多问题并行一次判"检索相关+grounded+是否幻觉"
    System1/System2CoALA（2309.02427）/ LLM2（NAACL 2025）System1 快生成/快判定、System2 慢推理/审慎Jev 是 CoALA 里一直空缺的"System-1 判定子程序"实现
    校准 / 选择性预测Conformal 入门（2107.07511）/ HCMA（2410.02173）/ To Believe or Not（2406.02543）弃权 20% query 把错误率砍 30%，仅需 50–100 样本校准；要区分 epistemic vs aleatoricJev 概率当门限前必须过的三关：校准、OOD、"不知道"vs"多解"

    Jev 的真实增量与未验证点

    维度现有成熟工作Jev 新形态增量 / 风险
    判定粒度单输入→单判定/单路由单 pass→多问题并行增量：批量省延迟；风险：多问题是否互相串扰，文献无现成答案
    输出形态文本/分数/logprob原生概率分布增量：直接当门限；风险：校准与 OOD 可靠性未验证
    是否生成文本多数带 CoT 理由完全不生成增量：极致便宜快；风险：失去可解释性、难 debug
    升级/弃权靠 logprob/agreement 凑置信度原生概率直接驱动增量：免多次采样；风险：见校准三问

    文献给 Jev 落地前的前置验证清单：①在真实分布上画 reliability diagram、算 ECE，用 50–100 样本做温度/logistic 校准；②用 Leave-One-Dataset-Out 协议测 OOD（同分布指标会高估约 8.4pp）；③自做多问题独立性 ablation；④Jev 必须独立于被判定对象（自证无效）；⑤区分"不知道"与"多个都合理"，否则门限误杀。

    中文与跨语言支持证据

    本项目场景是中文法律卷宗，这一节是决定性约束。

    官方口径：只背书英文官方宣称

    官方 Models 页原文："English is the primary training language and where accuracy is currently best. Other languages, including CJK scripts, are handled but not equally well; test on your own content before relying on Jev for a non-English workload, and pay close attention to Confidence when routing." 即：中文输入不会被拒绝、可直接写进 state/question，但官方不给中文准确率数字、所有文档示例均为英文、并明确要求非英文场景先用自有数据自测。

    第三方中文实测：短文本约 64%，落后国产模型第三方实测

    虎嗅/硅星人 2026-09-20 的对照（50 条真实中文电商客服问题，每条 4 项判断、全对才算对）：Jev 平均 32/50、完整准确率约 64.0%–65.2%、平均每题 0.75 秒、50 题约 $0.0020；同批题上 GLM 5.3 Flash 90.4%、Qwen 3.8 Flash 85.6%、Kimi K3 83.6%、GPT-5.5 76.4%。含义：Jev 在短中文题上不是"最强中文判断模型"，而是"最便宜最快但准确率垫底"的那个，国产中文模型比它高 20–26 个百分点。另有阈值横跳：人工 2.00、Jev 1.99，重复 15 次有 3 道题在通过/失分间反复横跳。

    36氪/全天候科技 2026-09-21 的实测则呈现另一面：干净出题（绕开算术等已知短板）时 45/45 全对、三次一致；但把算账还给它时，贴线题 5 次全错且都报 8 成以上把握。两条看似矛盾，实则指向同一条：Jev 中文表现高度依赖"出题/选项设计"，没有鲁棒的固定准确率。另一个关键观察：同样篇幅，中文比英文折算 token 更多、更容易撞 32k state 上限（海尔中文版 5 次被接口拒收 vs 泡泡玛特英文版 4.4 万字符 10 次全对）。

    跨语言（中英混合）：证据不足待验证

    没有任何公开实测专门设计过"英文文档+中文提问/反向"的对照矩阵；官方对中英混合 state 无专门说明。混合检索进来的英文片段既可能稀释中文判定准确率、也可能成为注入载体——这正是必须自测的理由。长程浏览器实测另传 Jev 1/20 vs GPT-5.6 Luna 17/20（多步状态推演弱），属社区转述。

    对本项目的中文硬门槛判断

    🧭

    成本不构成障碍（满载 32k state 单次约 $0.00134、约 1 分钱）。真正门槛有三：① 32k 长度上限 + context rot，35 页整卷不能直塞、必须先检索分块；② 中文准确率与校准未在法律卷宗上验证；③ 官方自认注入式文字可移动答案，安全域零容忍。

    本项目机会映射（HarnessWindTunnel）

    📋

    项目背景：HarnessWindTunnel 是 AI Agent harness 的受控消融"风洞"（Agent = 模型 + harness），在建 Playground（#/playground）做 live 评估 + 自演化，场景为中国法院专利司法卷宗审理：35 页中文长卷宗 PDF + RAG 法条知识库 + 本地 patent-law-mcp；45 条任务分三域（通用 field-match / 法律 article-check / 安全 trap·gate·leak-check），三集固定 split（repair21 / gate15 / scorecard9），判分器确定性优先、LLM-as-Judge 兜底。成本现状：每次 run 约 30–80k tokens，演化每代 gate 约 30–90 个 run、约 1–7M tokens。本节仅用屏名 + hash 路由。

    P0 机会 A：L-MARS 引用断言五分类

    • 落在：法律屏（#/legal）的 Citation Fidelity Audit / Authority Library 相关控件。
    • 现方案：把每条引用断言打五类标签（supported / partially_supported / unsupported / citation_unreachable / no_citation），现在用 chat LLM 逐条判。
    • Jev 问题设计：state 放"断言句 + 所引法条原文片段"；用一个 Choice 问"该断言落在五类中的哪一类"（务必含 no_citation/citation_unreachable 出口）；同一份 state 再并行加一个 Score（0–5，引文对断言的支撑强度）与一个 Noul（"是否存在引用实际不可达却被当成 supported 的情形？"）。几十条断言一次 fan-out。
    • 预期收益：pointwise 封闭集多选一，结构化程度最高，天然 Choice；一次并行 map 几十条，省 N 次 chat 往返。官方数：13 问省 11.5×RAGBench 小模型胜 LLM-judge
    • 错误风险与兜底：中文法条准确率与校准未验证 → 先在 repair21 固定集跑一致性；低置信（如 <0.9）回落 chat LLM 复核；no_citation 出口必须保留。
    • 明确不适用：不能让 Jev 做法条语义三段论推理（jaggedness 第 4 条）。

    P0 机会 B：field-match / trap-check 判分兜底

    • 落在：Playground（#/playground），以及风洞屏（#/tunnel）的判分环节。
    • 现方案：field-match 语义不确定、trap-check 语义判定、groundednessCheck 生成后校验，现在用 chat LLM。
    • Jev 问题设计：state 放"任务期望字段/真值描述 + agent 实际产物"；一个 Choice（匹不匹配/部分匹配/不匹配）+ 一个 Score（语义吻合度 1–5，带具体 rubric）+ 一个 Noul（"产物是否被所给证据支撑？"）。每任务多次调用，频次高。
    • 预期收益：每次省一次 chat 往返；官方低时延（70–500ms 区间）对 Playground live 体验最对口。官方数Generative Verifiers Yes/No 概率验证
    • 错误风险与兜底：判分是"金标准"下游，错判污染成功率统计 → cascade：高置信直接定分、中置信加标记、低置信转 chat LLM；进 #/tunnel 对比面板时必须打来源徽标（jev-live vs llm-judge）。
    • 明确不适用：金额、编号、期间等精确比对留在代码侧（jaggedness 第 2、3 条）。

    P1 机会 C：失败标签批量归因

    • 落在：运行透视屏（#/insight）与演化屏（#/evolution）。
    • 现方案：13 个失败标签（premature-victory / fabricated-citation / scope-violation / unaware-of-stopping / step-repetition / context-loss / long-horizon-decay / fail-to-clarify / spec-misinterpretation / task-derailment / weak-grounding / reasoning-action-mismatch / other）现在基本靠 chat LLM 判。
    • Jev 问题设计：state 放一条轨迹回放摘要；一次并行问"是否 premature-victory？是否 step-repetition？是否 context-loss？……"——这正是 Jev 单 pass 并行多 question 的甜点位（13 个 Noul 一次出）。
    • 预期收益：把一条轨迹的归因从多次调用压成一次。SNIPS 97.9%、MetaTool 96.5%
    • 错误风险与兜底：艾特玖实测轨迹失败归因 AUROC 仅 0.560（随机水平）——跨步因果推理 Jev 做不了。只让 Jev 做"表层、可局部判断"的标签（step-repetition、context-loss），跨越多步的根因归因仍留 LLM；批量打标后在 #/evolution 的 PRISM 编辑面路由里新增"判定器一致性"证伪指标。
    • 明确不适用：需要理解整条轨迹因果链的归因。

    P1 机会 D：hook 裁决 / 权限三态路由预筛

    • 落在：安全屏（#/security）的权限三态路由（EXECUTE / ASK / REFUSE）与 hook（allow / deny / rewrite）。
    • 现方案：危险动作先分类再执行的 guardrail，目前落在 chat LLM / 规则。
    • Jev 问题设计：state 放"拟执行的工具调用 + 当前上下文"；用 Choice（该请求是否越权意图？是否注入？该走 EXECUTE/ASK/REFUSE 哪一档？）做预筛，高置信直接短路。
    • 预期收益：时延敏感、高频；LangChain AutoModeMiddleware 已是同款模式。官方宣称
    • 错误风险与兜底（最高优先）：安全场景漏报代价不对称，且官方自认注入可移动答案、LODO 论文显示 indirect 注入检测率仅 7–37%。门限必须偏保守、全部留痕；calibration 未验证前只做"旁路观察/打标"，不做"在线拦截"；任何 REFUSE 不自动放行 EXECUTE。
    • 明确不适用：对抗性强的 leak-check / 刻意构造的 trap 样本，不能只信 Jev 单判。

    P1 机会 E：RAG groundedness / rerank

    • 落在：#/playground 与知识库相关流程（知识库设置在 #/settings）。
    • 现方案：groundedness 判定用 chat LLM；rerank 用通用检索器。
    • Jev 问题设计：Score（该回答是否被该引文支撑，0–1）；rerank 用 Noul/Choice 式成对相关判定。
    • 预期收益：BEIR reranking MRR 0.622→0.843；RAGBench 证明小模型可在 RAG 评估上打败 LLM-judge。第三方实测论文实验
    • 错误风险与兜底：中文卷宗 + 中英混合检索片段未验证；先离线比对 rerank 顺序。
    • 明确不适用：HyDE、query 改写这类需要生成文本的环节。

    P2 机会 F：premature-victory 自查 / 循环检测 / 压缩预算点火

    • 落在：harness 内联判定（#/insight 运行时观察、#/tunnel 模块开关的在线指标）。
    • Jev 问题设计：内联 Noul——"agent 是否过早宣布完成？是否陷入重复循环？压缩预算是否该点火？"——时延敏感，Jev 低时延最对口。
    • 预期收益：卡位文献空白；但目前无成熟成功/失败案例可引用。待验证
    • 兜底：先离线回放历史轨迹跑命中率，再决定是否内联；误判成本低的可先上线观察。

    P2 机会 G：gate 批量重跑的结果筛选

    • 落在：演化屏（#/evolution）——每代 30–90 个 run 的评分解读与筛选。
    • Jev 问题设计：把"哪个 run 值得人看"做成批量 Choice/Score（一次并行 30–90 个）。
    • 预期收益：省的是人阅读成本而非 token。待实测
    • 兜底：只做"排序/推荐"，不做最终 gate 通过/拒绝；人控门保留。

    明确不适用点（必须显式排除）

    🚫

    任何需要生成文本的环节都不要碰 Jev：改动卡内容生成、簇 summary 撰写、HyDE、审理要点/裁判文书撰写、query 改写。需要长链推理的判定（复杂法律三段论）先列为待验证而非结论性替代；金额/编号/期间等精确比对留在代码侧。

    优先级矩阵与 Top 机会清单

    打分维度

    决策频次（高/中/低）× 单次判定消耗 token（大/小）× 判定结构化程度（高=天然 Choice）× 中文风险（中文证据缺口大小）× 实现难度（接入成本）。打分原则：频次越高、单次越贵、结构化越高 → 优先级越高；中文风险越高 → 越要先做最小实测再上生产。

    优先级矩阵（热力）

    机会点（屏 / 路由）频次消耗结构化中文风险难度综合
    A 引用断言五分类（#/legal）中小很高中低P0
    B 判分兜底 field-match/trap（#/playground、#/tunnel）高中高中低P0
    C 失败标签批量归因（#/insight、#/evolution）中中高（跨步弱）中高低P1
    D hook/权限三态预筛（#/security）高小高高（注入）中P1·仅旁路
    E RAG groundedness/rerank（#/playground、#/settings）高中高中低P1
    F 循环/完成/压缩点火（harness 内联）高小中中中P2
    G gate 批量筛选（#/evolution）低（每代）大中中低P2

    Top 机会清单（建议执行顺序）

    1. 先做 1–2 天最小实测（不直接上生产）：拿 #/playground 的 repair21 固定集，跑 A+B+E 三个 P0/P1，与现有 chat LLM 判分做同集 A/B，记录准确率、p50/p95、单次 token、置信度校准曲线、注入前后判定差值（含 0 注入与含注入配对 ≥20 条）。总调用约 200–400 次，成本 < $1。
    2. A 引用断言五分类：结构化最高、最稳，实测通过后优先接 #/legal。
    3. B 判分兜底：频次最高、省 chat 往返最直接，但必须带 cascade 与来源徽标。
    4. D 安全预筛只做旁路：calibration 验证前不做在线拦截。

    通过 / 失败判定线（建议，可按业务调整）

    指标通过线（建议）
    中文 Choice 准确率≥ 现有中文模型基线 − 5 个百分点
    含"无法判断"出口的拒绝正确率≥ 90%
    置信度校准报 80% 的样本实际正确率落在 70%–90%
    重复 3 次答案漂移率< 5%
    注入鲁棒性（一票否决）含注入 vs 无注入判定变化率 < 10%，注入检出召回 ≥ 90%；否则该场景禁用 Jev

    待讨论开放问题

    1. 中文证据不足期间，是否先拿 #/playground 的 repair21 固定集做 Jev 最小实测（1–2 天实验）再决定？
    2. 安全场景（#/security）对漏报零容忍，Jev 概率输出的 calibration 未验证前，是否只做"旁路观察/打标"、不做"在线拦截"？
    3. cascade 门限：低置信回落 chat LLM 的阈值定在哪（0.9？0.95？），abstain（other/"无法判断"）时如何兜底？
    4. 成本模型：Jev 按输入 token 计费后，一次并行 10 问的成本 vs 一次 chat 判定，哪个更省？需实测。
    5. 数据诚实铁律：Jev 判定结果进入 #/tunnel 对比面板时，数据来源徽标怎么打（jev-live vs llm-judge vs fixture）？
    6. 失败归因用 Jev 批量打标后，#/evolution 的 PRISM 编辑面路由是否需要新增"判定器一致性"这一维的证伪指标？
    7. ToU 争议：TypeSafe ToU 禁止公开发布 benchmark/性能数据——团队内部评测与对外报告 #/tunnel 对比面板时，数据披露口径需法务确认。
