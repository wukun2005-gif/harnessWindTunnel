    1 产品概述

    1.1 一句话定位与电梯陈述

    一句话：模型是引擎，Harness 是赛道。HarnessWindTunnel 让 Agent 开发者固定一个模型、一套任务，像吹风洞一样切换「Harness」配法——透视模型每一步实际看到什么，对 20 个 harness 模块做受控消融与反事实对比，并把一次失败炼成一条经过验证、人来批准、可回滚的Harness 改动。

    30 秒电梯陈述2026 年行业共识是 Agent = Model + Harness：模型趋同后，任务能不能可靠做完，越来越取决于模型之外的 harness（主循环、工具面、记忆、上下文压缩、校验器、权限门……）。但现有工具要么只回放单次运行轨迹（LangSmith 类），要么是黑盒自动改 harness 的研究代码（AHE / Harness-R1）。没有人给开发者一台「风洞」：在上线前用受控实验看清每个模块的边际作用，并在人的批准下让Harness可证伪地进化。HarnessWindTunnel 补的就是这一格，且默认面向写文档、数据分析、信息调研、跨应用工作流等非 coding 通用知识任务。

    1.2 背景与问题：为什么现在做、为什么值得做

    问题 1：可靠性瓶颈已从模型转移到模型之外。前沿模型在 SWE-bench Verified 上差距收窄到约 5 个百分点内；MAST 标注 7 个框架 1600+ 条轨迹归纳出 14 类失败（标注一致性 κ=0.88，arXiv:2503.13657），其中绝大多数是「配置问题」而非「模型笨」。早在 SWE-agent（arXiv:2405.15793）就已证明：固定模型与环境、只改面向 Agent 的接口，就能把 SWE-bench 从 12.5% 拉到当时 SOTA。

    问题 2：harness 模块「不是越多越好」，且作用随任务族、随模型反转，靠看单次 trace 永远发现不了。这是产品成立的硬证据：

    实证（来源）关键数字说明的问题
    NLAH 逐模块消融（arXiv:2603.25723）同一模型同一运行时、每次只叠一个模块：File-backed State +1.6/+5.5pp；Optimizer（NLAH 别名 Self-Evolution）+4.8/+2.7；但 Verifier 在 OSWorld 上 −8.4pp、Multi-Candidate 双任务族都为负凭直觉「加验证、加候选」会掉分，必须受控消融才看得见
    DeepMind AutoHarness（arXiv:2603.03329）模型排名随 harness 反转：Flash+合成 Harness 单人奖励 0.745 > Pro 0.707 > 裸 Flash 0.673；双人局对 Pro 胜率 56.3% 对 38.2%脱离 harness 无法给模型排名，必须做「模型 × harness」二维交叉
    Airbnb Beyond Prompts（arXiv:2609.05736，EMNLP 2026）固定模型只改 prompt + 工具边界中间件，非 coding 的函数调用 / 零售 / 电信客服任务平均提升 +14.2 / +14.9 / +10.1ppharness 增益对非 coding 业务任务同样成立，且闭源也能从 IO 边界接入
    Harness-R1（arXiv:2608.02276）反例让强模型直接改 harness，39 个有效补丁中 21 个让批次成绩变差（41.6%→35.4%，−6.2pp），仅 12 个变好黑盒全自动演化不可靠 → 产品必须「风洞证伪 + 人控批准 + 可回滚」

    问题 3：harness 正在被云厂商托管、黑盒化，反而更需要外部透视与版本回归。OpenAI 于 2026-09-10 公测 Agents API，把 durable session、自动压缩、recovery、tool search、服务端多 agent 等整套 harness 做成托管服务；它托管的是「通用均值」而非「对你任务的最优配法」，且官方会在用户不可见时持续改进 harness——同一任务会被悄悄改变行为，harness 版本回归从极客玩法变成生产刚需。

    1.4 价值主张：对谁有什么用

    Agent / Harness 开发者

    不再靠直觉堆模块或凭一次成功就上线。用受控实验回答「这个 verifier / 压缩策略 / 子 agent 到底帮没帮倒忙、值多少 token」，把每次失败沉淀为一条经验证、可回滚的配置改动。

    技术探索者 / 研究者

    一键复现 NLAH、AHE、Harness-R1、Airbnb PRISM 等论文结论，把「配对消融、模型×harness 交叉、可靠性下尾」这套学界已重复四遍却无产品的标准方法变成可亲手操作的实验台。

    演示 / 评审观众

    2 分钟看到「同模型同任务、两个 harness 终局 34% 对 77%」，并亲手拨动开关观察成绩与成本变化——把抽象的「Agent = Model + Harness」变成可观察、可干预的肌肉记忆。

    2 理论基础

    本文档是 PRD 的理论底座。先建立完整定义，再据此构建 demo 功能。

    2.1 核心公式

    Agent = Model + Harness

    Model 是推理引擎（GPT、Claude、Gemini……），提供”能做什么”的上限。

    Harness 是围绕模型的一切工程化控制——循环怎么跑、工具怎么给、上下文怎么压、失败怎么拦、人怎么介入。它决定模型的能力能不能稳定兑现。

    类比：模型是发动机，Harness 是赛道。同一台发动机在不同赛道上的圈速天差地别。

    量化证据： - 同一模型（gpt-5.4-xhigh）+ 同一任务，仅切换 harness 配置：34% → 77%（+43pp） - Harness-R1 论文：固定模型，Harness 优化平均提升 +10pp（arXiv:2608.02276） - NLAH 论文：Harness 模块消融实验，单模块最大增益 +5.5pp（File-backed State）

    2.2 Harness 模块体系

    2.2.1 设计原则

    Harness 不是一个黑盒，而是一个可拆卸、可拨动、可度量的模块系统。每个模块： - 有明确的接口（选项值有限、确定性） - 有论文或实验证据支撑（不是拍脑袋） - 可独立开关，不影响其他模块（正交性）

    2.2.4 确定性强制门（Enforced） vs 概率性引导（Guide）

    Harness 模块分为两类：

    类型 行为 代表模块
    确定性强制门（Enforced） 规则写死，Agent 无法绕过 ④ Sandbox、⑪ Permissions、⑬ Sensors
    概率性引导（Probabilistic） 通过 prompt 引导，Agent 可能遵守也可能忽略 ⑫ Guides、⑦ Memory、⑨ Skills

    这是本产品的关键区分点：wrappers ENFORCE / prompts REQUEST。大多数 Agent 框架只提供概率性引导（prompt engineering），本产品的硬价值在于确定性强制门。

    2.2.5 模块动态模型：模块→事件映射

    20 个模块是静态配置（拨开关时改什么），事件是运行时行为（执行过程中产生什么）。每个模块在运行时产生特定类型的事件，这些事件构成 Append-only 事件流，是运行透视、风洞消融、Forge 归因的数据根基。

    分组#模块运行时产生的事件事件说明
    Runtime Core①Loop Controlmodel.request model.response每轮循环：模型看到什么上下文（request）、回复了什么（response）
    ②Tool Surfacetool.call tool.result每次工具调用：调了什么工具、返回了什么结果
    ⑤SubAgent Isolationagent.fork agent.join子代理启动（fork：创建隔离上下文）与结束（join：结果回传主代理）

    ⑧Context Compressionshaper.fire compact.boundary压缩边界（compact.boundary：标记压缩点，记录压缩前后 token 数）与压缩器触发（shaper.fire：哪级压缩器生效、释放了多少 token）

    未列出的模块（③ FileSys、④ Sandbox、⑥ Planner、⑨ Skills、⑫ Guides、⑰ Eval、⑱ HITL（人在回路）、⑲ Resume、⑮ Policy）在当前离线 fixture 中不产生独立事件类型——它们的作用通过影响其他事件的参数来体现（如③ FileSys 影响 tool.result 的内容，⑥ Planner 影响 model.request 的上下文组成）。

    事件流的层次结构：

    run.started                          ← 运行开始
  ├─ model.request (step 1)          ← 模型看到的上下文快照
  │   └─ [① Loop Control 产生]
  ├─ model.response (step 1)         ← 模型回复
  │   └─ [① Loop Control 产生]
  ├─ hook.decision (step 1)          ← ⑩ Hooks 裁决
  ├─ permission.request (step 1)     ← ⑪ Permissions 请求
  ├─ tool.call (step 1)              ← ② Tool Surface 调用
  ├─ tool.result (step 1)            ← ② Tool Surface 结果
  ├─ verifier.verdict (step 1)       ← ⑬ Sensors 验证（重语义）
  ├─ sensor.lint (step 1)            ← ⑬ Sensors 轻量检查（确定性规则）
  ├─ shaper.fire (step 1)            ← ⑧ Compression 触发
  │   └─ compact.boundary            ← ⑧ Compression 压缩边界
  ├─ agent.fork (step N)             ← ⑤ SubAgent 启动
  │   └─ agent.join (step M)         ← ⑤ SubAgent 结束
  ├─ failure.tag (step N)            ← 叙述者事后标注（author=narrator，见下）
  └─ run.finished                    ← 运行结束

    这个事件流是确定性的、可回放的：给定同一组事件，运行透视、风洞对比、Forge 归因的每一步都可精确重建。这正是"风洞"方法论的物理基础——实验数据不是黑盒日志，而是结构化的、可审计的事件序列。

    事件作者（author）：每个事件带 author 字段，取值为 harness（被测 Harness 在运行时产生）或 narrator（叙述者事后标注）。离线 fixture 模式下，只有 failure.tag 的作者是 narrator（由剧本在犯错步骤后手工贴标，其余事件作者均为 harness——裸 baseline 分支也有 failure.tag 恰好证明了这一点）。评估 Harness 行为（消融读数、干预计数）时只认 author=harness 的事件；运行透视把 narrator 事件单列在"失败标注"区，不计入"Harness 干预"。Live 模式下以事件自带的 author 为准：Harness 自身的传感器也可能产生 failure.tag（此时 author=harness），与叙述者标注严格区分。

    每个 Hook 事件可以挂多个 handler，通过 matcher 过滤器控制”哪种工具调用时触发”：

    "PostToolUse": [
      { "matcher": "Edit|Write", "hooks": [{ "command": "check-style.sh" }] },
      { "matcher": "Bash",       "hooks": [{ "command": "check-security.sh" }] },

    24 种事件类型 × 常见 matcher 组合 ≈ 30 个常用 hook。这就是 PRD 中”~30 个确定性生命周期钩子”的来源。

    2.4 上下文压缩：5 级 Shaper 级联

    2.4.1 问题

    Agent 的上下文窗口是有限的（如 128k tokens）。随着对话推进，上下文不断膨胀。如果不压缩，会出现： - 上下文溢出：超出窗口限制，早期信息被强制丢弃 - 长程衰减：中间部分的信息被挤出，导致 U 形注意力曲线中段召回下降

    2.4.2 五级级联

    压缩管线按从便宜到昂贵的顺序依次尝试：

    级别 名称 策略 成本 触发条件
    ① Budget 预算溢出裁剪 最低 上下文超过 token 预算
    ② Snip 修剪历史 低 Budget 不够时
    ③ Microcompact 微粒度压缩 中 Snip 不够时
    ④ Context Collapse 只读折叠投影 高 Microcompact 不够时
    ⑤ Auto-compact 语义摘要兜底 最高 前四级都不够时

    2.4.3 Context Collapse 详解

    Context Collapse（上下文折叠）是第 4 级压缩，也是最接近”理解”的压缩方式：

    • Budget/Snip = 删除（丢弃旧消息）
    • Microcompact = 缩小（压缩单条消息的 token 数）
    • Context Collapse = 重组（把多条相关消息合并成一条精炼总结）

    “只读投影”的含义：原始完整历史仍然存在（只读），但模型只看到压缩后的投影版本。就像把 100 页会议记录整理成 10 页摘要——保留关键信息，去掉冗余。

    2.4.4 实际效果

    配置 压缩策略 成功率 说明
    fivelayer 五级全开 61.5% 从廉价到昂贵逐步压缩，保留最多信息
    budget 仅第 1 级 58.9% 只做最粗暴的裁剪
    nocomp 不压缩 22% 上下文溢出直接导致任务失败

    2.5 失败检测标签体系（对齐 MAST）

    2.5.1 标签从哪来

    MAST（Multi-Agent LLM System Taxonomy）来自伯克利论文《Why Do Multi-Agent LLM Systems Fail?》（arXiv:2503.13657），是一套 Agent 失败模式分类体系，用于检测和归类 Agent 在执行任务时的失败。原论文定义 14 种失败模式（编号为 FM-1.1～FM-3.3，分属 FC1 系统设计、FC2 智能体间错位、FC3 任务验证三组，附各模式在 1642 条轨迹中的占比；原论文没有 1～14 的流水编号，此前文案中的“#14”系误写，已更正为 FC3）。本产品保留 12 个一等标签＋1 个 other 兜底：前 6 个自下而上从 5 个场景的 Trap 长出来（2.6.4：全部场景 Trap 恰好完全落入这 6 个标签），再到 MAST 及其他来源里找对应、找依据；后 6 个来自 MAST 14 类复查（2.5.4），为检测完整性补齐，全部直接对上 MAST（步骤重复＝FM-1.3，不知停止＝FM-1.5，任务脱轨＝FM-2.3，未问澄清＝FM-2.2，上下文丢失＝FM-1.4，推理行动错位＝FM-2.6，见下表映射列与 2.5.4 复查表）。other 只剩 4 种未映射的原文模式（FM-1.2、FM-2.1、FM-2.4、FM-2.5，均为多智能体协作特有且低占比）。取舍理由：FC2 整组描述多智能体协作错位，当前 5 个场景均为单智能体执行、无此运行形态可观测；其余单智能体相关模式已全部升为一等标签，不再有缺口。

    2.6 Trap、Failure Mode、失败标签的关系

    2.6.1 三层分类体系

    本产品有三层不同的”失败”概念，容易混淆：

    层级 名称 谁定义 数量 作用
    场景层 Trap（陷阱/诱因） 每个场景自己定义 不固定（每场景 2-10 个） 描述”这个场景可能怎么失败”
    系统层 失败检测标签 MAST 体系＋任务族综合定义 固定 12+1 种 描述”检测到的失败属于哪种模式”
    结果层 Failure Mode（失败模式） run.finished 汇总 来自失败标签 最终统计”这个分支有多少种失败”

    2.6.2 映射关系

    一个 Trap 可能映射到一个失败标签，也可能一个失败标签覆盖多个 Trap：

    场景: writing-q3-report
  Trap: "长上下文溢出"        ──→ 失败标签: long-horizon-decay
  Trap: "长程后段质量塌陷"     ──→ 失败标签: long-horizon-decay（同一个）

场景: research-competitor-scan
  Trap: "没查全就下结论"      ──→ 失败标签: premature-victory
  Trap: "编造引用"            ──→ 失败标签: fabricated-citation

    2.6.3 为什么 Trap 和失败标签不是一一对应？

    • Trap 是场景视角：从任务特性出发，描述”可能出什么问题”（如”长上下文溢出”是报告写作场景特有的风险）
    • 失败标签是检测视角：从失败模式出发，描述”怎么分类检测到的失败”（如”long-horizon-decay”是通用的长程衰减模式）
    • 一个 Trap 可能触发多种失败标签，一个失败标签也可能覆盖多个 Trap

    2.7.3 本产品的独创性

    本产品不发明基础理论——MAST、MemGPT、CoALA、NLAH、VeritasBench 等来源提供了模块和概念。本产品的独创性在于：在这些别人的工作之上，搭建和定制了自己需要的理论框架，并在这个框架基础上 build 了这个产品。

    具体而言：

    • 统一 DSL：将 NLAH、Claude Code、MemGPT、MAST 等来源的零散概念提炼为 20 字段可配置 DSL——不是发明新模块，而是定义了一套统一的配置语言
    • 模块分组：将 20 模块按职责归入 4 大分组——不是发明新的分类维度，而是为本产品的交互设计选择了最合适的组织方式
    • Trap → 失败标签映射：建立场景级诱因与系统级检测标签的关联——6 标签自下而上从场景 Trap 长出（2.6.4），再到 MAST 及其他来源找依据（2.5.2 映射列），不是 MAST 原文的直接子集
    • 确定性 vs 概率性：借鉴 VeritasBench “wrappers ENFORCE / prompts REQUEST” 框架，但将其从论文概念转化为产品中可操作的设计原则
    • 交互化消融：将论文中的受控消融实验（NLAH、AHE）转化为可上手拨动的交互式 demo——不是发明新方法论，而是让学术方法论变得人人可用

    一句话：站在巨人肩膀上，为自己的产品搭了一套适用的框架，然后把框架变成了可交互的产品。

    双轨运行架构：离线确定性回放 + 在线真模型

    离线档（默认 · 零成本 · 100% 可复现）

    预置四类知识任务族各 1–2 个 golden 场景 + 1 个 coding 对照；每个场景 × 若干 harness 配置预录 fixture 轨迹分支。回放器（server/replayer）按 HarnessConfig 指纹选分支，指纹不命中时回退到汉明距离最近分支并显式提示 nearestTo，保证演示永远稳定可复现、不依赖网络与密钥。

    在线档（可选 · 用户自配 LLM Provider）v1.1 改

    Node 侧实现最小真实 harness（主循环 + 3–4 个工具、可切换压缩与 verifier 策略），用用户自己配置的模型真跑，用于验证「这不是只对写死的数据成立」。不绑定任何厂商：Provider 配置界面（厂商预设 + 自定义 OpenAI 兼容端点、apiKey / baseUrl / 模型列表 / 默认模型 / fallback、拉取模型与验证）及其持久化整体照搬现成 docStudio 工程（详见第 5 章 F4-6 与第 8 章在线 Provider 设置）。在线结果与离线 fixture 在 UI 上以来源标签明确区分。

    诚实原则（不可妥协）论文预设数字标注来源与「脚本复现」，fixture 示意数据标注「示意」，绝不把 mock 说成实测；每条指标带来源（fixture / paper-reproduction / live）与引用（SourceRef）。这沿用作者既有 appUIRefiner「不假装已生效」原则，也是本产品区别于「造好看假数据 demo」的底线。

    受控实验的物理底座：沙箱快照分叉

    严格的反事实对比要求「除 harness 外一切相同」。调研报告 4.6 节指出，现代 agent 沙箱把四个状态操作做成一等公民：snapshot（快照）/ clone·fork（分叉）/ rollback（回滚）/ pause-resume（暂停恢复）（腾讯 CubeSandbox、清华×月之暗面 AgentENV、E2B、阿里 OpenSandbox）。风洞屏二的「同任务双配置逐步 diff」在工程上应建立在从同一黄金快照分叉 N 份、分别跑不同配置、跑完即弃、可回滚重放之上，而非每次手工重搭环境。

    ① 黄金快照固定任务输入、工作区、依赖、初始状态，打不可变 snapshot
    ② clone N 份从同一快照分叉，每份注入一个 harness 配置（A/B/C…）
    ③ 并行运行各分支独立执行，凭证由网关注入、不进沙箱
    ④ 对齐读数同步对齐轨迹、计算 lift 与下尾，分支跑完即弃 / 可 rollback 重放

    v1.1 离线档用「预录分支」等价实现快照分叉的可复现效果（不真正起 microVM）；在线档与 Stretch 再对接真实沙箱 API。注意隔离的是执行过程，产物通过受控通道（diff / 文件 / 快照）回传，因此「被隔离」不等于「结果用不了」。

    Lift（scorecard 提升；留出为别名）在没参与优化的 scorecard 集（别名 holdout / 留出）上，候选配置相对基线的得分差。「留出」即修复、选配置时都不许看这套题，只在最终记分用，防止对着期末答案调参这套改动在新题上是否真的更好
    MeanLift / MaxLift多次运行 Lift 的平均 / 最好一次平均收益 / 运气最好的上限
    WorstLift多次运行里最差一次的 Lift（可为负＝改完更差）最坏的单次运行会多糟
    RR₀多次运行中 Lift>0 的占比（可重复性 / 胜率）这次提升稳不稳、是不是偶发
    Cost搜索 / 实验过程消耗的模型调用与 token 成本为提升付了多少代价
    RelLift₉₅(B)预算 B 下、只凭「记分前可见的 gate 集」挑一个配置，被选配置在 scorecard 集上 Lift 分布的第 5 百分位（倒霉情形还剩多少增益）；真实 run 少时用 5000 次 bootstrap 估计，不新增真实 run、不额外花钱把「按验证集择优」这个动作本身的风险也算进去后的保守下界
    Skill Lift（配对）同 agent/model/task/workspace/grader 下，有 / 无某模块的配对差（NVIDIA ACES，arXiv:2608.20614）单个模块的纯净边际作用

    适配度指标（固定 harness、变换 model，服务 F2-11）v1.1 新增

    第二条评测轴锁定 HarnessConfig 与任务集（configDiff=0、seed / 工具 / 评分器全部冻结），只换模型，衡量「这套Harness与不同模型合不合拍」：

    指标定义回答什么
    Model-Conditional Lift（模型条件增益）固定 harness h、模型 m，在 scorecard 集上 score(h,m) − score(Bare Baseline, m)；正＝这套Harness对 m 是加成，负＝不合拍、反而拖累这套Harness对「这一个」模型是帮忙还是帮倒忙
    Compatibility Spread（适配离散度）同一 h 跨全部被测模型得分的极差（max−min）与标准差这套Harness「挑不挑模型」、可迁移性强不强
    Rank Robustness（排名稳健度）该 harness 下的模型排序与其 Bare Baseline 排序（别名裸跑）的一致度（排名反转对数 / Kendall τ）；AutoHarness 里 Flash+harness 反超 Pro 就是一次反转换Harness会不会改变模型强弱排名
    Cross-Model WorstLift / RR₀把可靠性下尾的「多次运行」维度换成「多个模型」：最差一个模型上的条件增益、以及条件增益为正的模型占比换到一个没专门测过的模型会不会崩
    合拍分级：推荐搭配＝各模型 Model-Conditional Lift 均为正且 Cross-Model WorstLift ≥ 0；可搭＝平均为正但 Spread 偏大；谨慎搭配＝存在模型为负（明确点名是哪个模型）

    与 F2-4 同源不重算：F2-4 是「行=模型、列=harness」矩阵的纵向读法（固定模型看不同 harness），F2-11 是横向读法（固定一列 harness 看不同模型），两者来自同一批 run，禁止各算一套导致数字打架。理论支点：AutoHarness（arXiv:2603.03329）、HarnessDev 跨 executor 崩塌 69.3→33.0、Harness Sensitivity is Non-Monotone（arXiv:2605.26731，432-run / 6 模型 × 4 能力档 × 3 严格度，证明同一 harness 对不同模型增益非单调）。

    端到端算例（数字可复现：随机种子 42、重采样 5000 次）

    某候选配置相对基线，在 scorecard 集上 8 次独立运行的 Lift（单位 pp）为：

    Lift = [ +6, +4, +8, −3, +5, +7, +2, +3 ]
    指标取值怎么算 / 怎么读
    MeanLift+4.0 pp(6+4+8−3+5+7+2+3)/8 = 32/8
    MaxLift / WorstLift+8 / −3 pp最好一次 +8；最差一次反而掉 3 分
    RR₀87.5%8 次里 7 次为正
    RelLift₉₅（bootstrap）≈ +2.1 pp对 8 个值有放回重采样 8 个求均值、重复 5000 次得到「均值分布」，取第 5 百分位 = +2.12（P50=+4.0、P95=+5.75，重采样均值<0 仅 0.1%）

    为什么需要 bootstrap、WorstLift 与 RelLift₉₅ 怎么选真实 run 往往只有个位数到十几个，直接取「第 5 百分位」极不稳；bootstrap 对现有配对差有放回重采样来稳定估计均值的抽样分布，不增加真实 run、不多花钱。WorstLift 是「单次运行」的极端值，最悲观、对 run 数敏感；RelLift₉₅ 是「平均增益」的下尾，回答「整套配置在倒霉情形下总体还剩多少增益」，本例虽有一次 −3，平均下尾仍为 +2.1。口径选择：当候选多、每个候选测试充分完整时，可直接以 WorstLift 为决策口径（更严格、无「赌」的成分）；当 run 预算紧、需要在「择优风险」与成本间权衡时用 RelLift₉₅。产品两者并列展示，把选择权交给用户，不替用户赌。

    防过拟合：repair / gate / scorecard 三数据集隔离

    repair 修复集只用于看失败、生成改动卡（学习 / 拟合）
    gate 筛选集只用于在多个候选间择优（记分前可见）
    scorecard 集只用于最终记分，优化过程全程不可见

    三套互不相交，防止「对着期末答案调参」；RelLift₉₅ 中的「只凭 gate 择优、到 scorecard 才见分晓」正是对这套隔离的量化。UI 在任何实验 / 演化界面都要标明当前跑的是哪一套数据集。
